# 缓存友好上下文截断：设计说明

## 目标

为每个 Daddy 助手增加一个可手动开启的“缓存友好截断”方式。无限制上下文和现在严格保留最近消息的方式都必须继续保留，且默认行为不变。

## 你会看到的行为

- 开关属于“助手设置”，因为“上下文消息数量”本来就是每个助手单独设置的。
- 在上下文消息数量旁边增加“缓存友好截断”开关。
- 当上下文为无限制（`0`）或少于 `200` 条时，开关置灰不可开启，并说明“仅在上下文上限达到 200 条时可用”。
- 所有已有和新建助手的开关默认关闭。
- 开关关闭时，Daddy 完全保持现在“严格取最近 N 条”的行为。
- 开关开启且上限不少于 `200` 条时，每次按上限的 **25%** 阶梯裁剪：
  - 上限 `200`：每次裁剪后保留约 `151` 到 `200` 条。
  - 上限 `400`：每次裁剪后保留约 `301` 到 `400` 条。
  - 上限 `500`：每次裁剪后保留约 `376` 到 `500` 条。
- 这个功能不会删除或摘要任何原始聊天、分支、Supabase 数据、Ombre 记忆、世界书或管理记忆；它只决定“本轮发给模型的当前窗口聊天记录”。

## 裁剪规则

`limitContext(limit, cacheFriendly)` 在无限制，或当前消息数尚未超过上限时，直接返回全部消息。

当缓存友好截断不可用或开关关闭时，继续使用当前的严格滑动窗口逻辑，并保留现有工具调用边界保护。

当开关开启时：

1. 计算裁剪步长：`stride = round(limit * 0.25)`。
2. 计算超出的消息数：`overflow = 当前消息数 - limit`。
3. 起点前移：`ceil(overflow / stride) * stride` 条。例如上限为 `400`：第 `401` 条出现时，跳过最早的 `100` 条并保留 `301` 条；到第 `500` 条时仍保留 `400` 条；第 `501` 条时才再次前移 `100` 条。
4. 将起点向前回退到安全的工具边界。一次工具请求、它的结果和发起它的用户消息不能被拆开；必要时允许实际发送的消息数略高于名义上限，优先保证工具链完整。

两次阶梯裁剪之间，起点保持不动。新增的用户或 Daddy 消息只会追加在末尾，模型就能连续复用相同的请求前缀缓存。发生裁剪的那一轮缓存可能暂时下降，之后的多轮会重新稳定复用新的前缀。

## 本次不会改动的内容

本次只处理“当前窗口的聊天历史”。不会改变固定人设、世界书、管理记忆、Supabase 召回、Ombre、健康提示、工具、插件、连续性提示或九维欲望的位置与行为。

“把动态召回尽量后置”是另一项未来优化，需要单独测量 DeepSeek 的实际缓存数据，不能和本次裁剪混在一起。

## 保存与兼容

在助手配置中增加一个默认值为 `false` 的布尔字段。旧版配置、备份和导入的助手都能安全读取，并保持今天的默认行为。切换开关不会修改你原本设定的上下文消息数量。

## 异常与边界

- 即使旧配置或手动编辑的配置把开关设为开启，只要上限少于 `200` 条，Daddy 仍按原来的严格方式工作。
- `0` 或负数仍表示无限制。
- 工具链完整性永远优先于严格条数。

## 验证方式

单元测试必须覆盖：

- 开关关闭时的现有严格行为。
- 无限制和少于 `200` 条时，开关不会生效。
- `200`、`400`、`500` 三种上限在第一次与第二次裁剪前后的精确边界。
- 缓存友好模式下工具结果与工具调用的完整性。
- 新助手字段的默认值与旧配置兼容。

最终 APK 验证：开关在少于 `200` 条时不可用、在 `200` 条时可用、每个助手独立保存，并确认无限制上下文完全不变。
