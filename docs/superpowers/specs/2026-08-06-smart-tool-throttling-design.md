# Daddy 智能工具节流（试用版）设计

## 目标

在不改变 Daddy 的人格、世界书、记忆系统、插件页面或用户自选聊天上下文条数的前提下，减少普通聊天每轮发送给模型的无关工具定义。

用户当前观察到：新窗口首条约 38k token，90 条上下文的普通消息约 50k token。检查发现，互动聊天会把所有已加载插件工具和当前助手关联 MCP 的所有已启用工具一起加入请求；已安装插件的 manifest 合计约 72 KB，其中共读书房单独声明 14 个工具。

## 已确认的用户体验

- Daddy 的“上下文消息数量”仍由用户自行设置（例如 60、90、100 或不限）；本功能绝不修改该设置，也不会自动压缩对话。
- 新增可随时开关的“智能工具节流”。关闭时必须保持当前完整工具行为。
- 开启时，未命中的能力不随每轮请求发送；用户可在发送前点击“本次全工具”，仅让这一次发送带上完整工具集。
- 不使用额外模型调用来识别场景，避免用省下的 token 换来一次分类调用。
- 首版只影响用户手动发送的普通聊天；晚安守夜、激进模式与其他主动消息沿用现有工具构建逻辑。

## 方案比较

### 方案 A：让用户手动禁用插件

实现最小，但插件能力会真的失去，且每次要用又要进设置重新启用，不符合“能力还在”的目标。

### 方案 B：本地场景路由（采用）

在发送前用当前用户文字和结构化内部标签做本地关键词匹配，为本轮选择核心工具和对应场景工具。无网络、无模型调用、延迟极低。未命中时用户可单次选择完整工具集。

### 方案 C：先请求模型分类再装载工具

识别更灵活，但需要增加一次模型请求、延迟和 token，不适合作为省 token 的默认路径。

## 架构

```text
用户输入 + 本次全工具临时标记
            |
            v
      SmartToolRouter（纯 Kotlin）
            |
  节流关闭 / 单次全开 ------> 原完整工具集
            |
            v
  核心工具 + 命中场景的工具子集
            |
            v
       GenerationHandler / 模型请求
```

### 配置与状态

- 在 `Assistant` 增加持久化布尔字段 `smartToolThrottlingEnabled`，默认 `false`，以保证旧备份和现有助手完全维持原行为。
- “本次全工具”是聊天界面的临时状态，不写入助手设置、不写入聊天记录；发送完成后立即清除。
- 节流开关由当前助手保存，因此同一个 Daddy 的所有聊天窗口共享开关状态，用户仍可在助手设置中随时改变。

### 核心工具

节流开启时，核心组保留：

- 本地记忆工具与已启用的 Skill 入口；
- 用户当前开启的基础工具中，与时间、消息处理和常规聊天直接相关的工具；
- Ombre-Brain 的日常记忆工具：`breath`、`breath_search`、`hold`、`grow`、`plan`、`trace`（以工具原始名称匹配）。

未归入核心的 MCP 工具和插件工具只有在场景命中时进入该轮请求。若某个核心工具不存在，路由器不报错、直接跳过。

### 场景映射

路由器仅根据本条用户输入和内部文本标签匹配，不检查聊天正文历史。首版关键词集可维护且保守：

| 场景 | 触发词或标签 | 本轮加入能力 |
|---|---|---|
| 共读 | `书房来讯`、共读、章节、批注、书签、这本书、页码 | 共读书房插件全部工具 |
| 路线与地点 | 路线、导航、怎么去、附近、地点、地铁、公交 | 高德 MCP 工具 |
| 健康 | 睡眠、心率、步数、血氧、压力、卡路里、手环、健康数据 | 健康/Gadgetbridge 与 LoverConnect 相关工具 |
| 日记与记忆 | 日记、候选、总结、记住、存一下、承诺 | 日记插件与 Ombre 核心工具 |
| 日常记录 | 喝水、经期、姨妈、周期、待办、任务、清单、朋友圈、钱包 | 对应生活插件工具 |
| 终端与文件 | Termux、终端、命令、脚本、文件、运行、安装、日志 | Termux 桥插件工具 |
| 天气 | 天气、下雨、温度、带伞 | 天气插件工具 |

多个场景可同时命中。未命中的插件不会进入模型工具定义，但插件自身页面仍可正常使用。

### 用户界面

- 在聊天输入区现有工具入口中加入「智能工具节流」开关，显示当前助手的持久化状态。
- 当节流开启时，在同一入口提供「本次全工具」动作；点击后显示本次已全开，发送后自动恢复。
- 开关关闭时不显示“本次全工具”，因为本来就是完整工具集。
- 首版不承诺精确 token 计数；可显示“本轮工具：精简 / 全部”的状态，避免给出不可靠的本地估算。

## 兼容性与失败处理

- 节流关闭的代码路径直接复用现有完整工具构建逻辑，保证旧行为不变。
- `Assistant` 新字段有默认值，旧备份导入后保持关闭节流。
- 路由器对未知工具、未连接 MCP、未安装插件返回空匹配，不影响消息发送。
- 任何场景匹配失败都不会阻塞发送；用户可使用“本次全工具”重发或继续提问。
- 不改变 MCP 服务本身的启用状态，也不禁用插件；只决定某轮是否把它们的 schema 发送给模型。

## 测试策略

- 为纯 Kotlin 路由器写 JVM 单元测试：关闭节流返回完整集、单次全开返回完整集、各场景关键词命中正确工具、多个场景合并、未知输入只保留核心、缺失工具安全跳过。
- 为聊天工具构建增加覆盖：普通聊天接入路由器；主动消息不接入。
- 构建 companion APK，并验证安装包包名、版本和签名。
- 在手机上手测：同一句普通闲聊在开/关节流时的工具数量变化；共读批注、路线、健康、Termux 与“本次全工具”各一条。

## 成功标准

- 节流关闭时与当前版本同样能调用完整工具。
- 节流开启时，普通闲聊不携带共读、日记、路线、Termux 等无关工具。
- 相关话题仍能自动得到对应工具；用户随时可单条发送全工具兜底。
- 90 条上下文设置可继续由用户自由调整。
- 预计显著降低首条与普通聊天的输入 token；具体数值取决于实际 MCP schema 与动态记忆长度，不作为固定承诺。
